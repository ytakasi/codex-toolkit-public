# 仕様実装準備チェックリスト

物語、分岐、状態管理、意思決定フローの仕様を実装前に点検するための reference。
全部を毎回読む必要はない。曖昧さがありそうな領域だけ使う。

## 判定

### No-Go

- route / ending / state の到達条件が自然文だけで、実装条件へ落とせない。
- ID 体系がなく、event、fact、memory、flag の重複や混同が起きそう。
- 既知情報、取得情報、UI表示情報、内部状態の境界が曖昧。
- 仕様上の制約を破ると、物語やdomainの意味が変わる。
- 圧縮、統合、削除、簡略化などの副作用で詰みや情報喪失が起きうる。

### Conditional Go

- 最小縦 slice の範囲なら条件や状態が決まっている。
- 未決事項が `Open questions` として明示され、実装範囲から外せる。
- 仮IDや仮状態を使う場合、後で正規化する場所が分かっている。
- UI表示は仮でも、内部状態と保存値の互換性を壊さない。

### Go

- 分岐条件、状態遷移、ID体系、UI surface が実装者に伝わる粒度で定義済み。
- リポジトリ固有の世界観制約が、少なくともテスト観点や禁止事項へ落ちている。
- 未決事項が実装範囲外か、通常の実装判断として扱える。

## チェック観点

### 目的と制約

- 仕様の成功条件があるか。
- 何をしてはいけないかが、禁止事項だけでなく判定観点になっているか。
- domain固有名詞を消しても、制約の種類を説明できるか。

### 分岐条件

- route / ending / event unlock の条件があるか。
- `allOf`、`anyOf`、`not`、count、priority、fallback のどれに近いか説明できるか。
- 条件の競合や同時成立時の優先順位があるか。
- 条件未達時の扱いがあるか。

### 状態遷移

- 状態一覧があるか。
- 許可される遷移と禁止される遷移があるか。
- 失敗、保留、解決、取り消し、再開の扱いがあるか。
- save / resume / migration に響く状態名が安定しているか。

### ID と data model

- ID の命名規約があるか。
- 人間向け表示名と機械可読な識別子が分かれているか。
- event、memory、fact、flag、item、task などの責務が混ざっていないか。
- 参照先が消えた時の fallback や validation があるか。

### UI surface

- UI に表示する情報と、内部状態に留める情報が分かれているか。
- locked、unknown、hidden、resolved、failed などの表示状態があるか。
- プレイヤーやユーザーに見せる順番が仕様上重要か。
- 表示文言変更が保存値や外部契約を壊さないか。

### 情報境界

- 登場人物やシステムが最初から知っている情報と、行動で得る情報が分かれているか。
- 取得リソース化してはいけない既知情報がないか。
- 隠し情報や真相の開示順を、flag や状態として扱えるか。

### 失われる操作

- merge、compress、discard、skip、auto-resolve などの不可逆操作があるか。
- 必須情報が失われると詰む設計になっていないか。
- 失われたことをUIやログで説明する必要があるか。

## 出力で分けるもの

- `Must fix before implementation`: 実装前に決めないと data model や仕様解釈が壊れるもの。
- `Can defer`: 最小縦 slice では外せるが、後で決める必要があるもの。
- `リポジトリ固有として残す`: 共通化せず、そのリポジトリの設計資料や AGENTS に残すべきもの。
- `Open questions`: ユーザー判断が必要な問い。
