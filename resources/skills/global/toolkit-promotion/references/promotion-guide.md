# 共通化・昇格ガイド

個別リポジトリで生まれた skill / template / 運用ガイダンスを、いつ `codex-toolkit` に上げるかの判断基準。

## 昇格させてよいもの

次のうち複数に当てはまるなら、共通化候補。
ただし「2リポジトリ以上で実績がある」は強い根拠であって必須条件ではない。
リポジトリ固有名詞を剥がしても意味が通り、次の作業の質を上げるなら、小さい形で先に昇格してよい。

- 2リポジトリ以上で再利用できそう
- リポジトリ固有の業務知識に強く依存していない
- 同じ失敗や迷いを何度も防げる
- 数週間後にも使う見込みがある
- 短く一般化して説明できる
- 既存 skill の `references/` や `assets/` に小さく吸収できる
- 既存skillを複数またぐ順番や入口があり、その流れ自体を再現したい

## まだ昇格させないもの

- その product だけのドメイン判断
- 一度しか使わない応急処置
- 秘密情報や環境固有パスを含むもの
- 仕様がまだ揺れていて、名前すら安定していないもの
- 「なんとなく便利そう」だけで、再利用場面がまだ見えていないもの
- 置き場所、名前、責務境界がまだ不明で、既存 skill にも安全に吸収できないもの

## どの形式にするか

| 置き場所 | 向いているもの |
|---|---|
| 共通ルールテンプレート `resources/global/AGENTS.common-rules-template.md` | 全リポジトリで常に効かせたい、自分の標準方針 |
| リポジトリの `AGENTS.md` | そのリポジトリだけの常設指示や例外 |
| `skill` | 何度も実行する手順、呼び出し条件がある作業フロー |
| `template` | 新規リポジトリや新規ファイルの初期形 |
| `skill` 配下の `assets/` | skill と一緒に使う雛形や開始文 |
| skill 配下の `references/` | skill に従属する背景、判断基準、導入手順などの説明 |
| `references/revisit-candidates.md` | 名前、置き場所、責務境界が未確定で、まだ昇格しない候補の一時保留 |

## 迷った時の簡易判定

- **次のリポジトリでも自分が同じことを言いそうか？**
  - Yes → 昇格候補
  - No → リポジトリ固有でよい
- **説明する時に product 名を消しても意味が通るか？**
  - Yes → 共通化しやすい
  - No → まだ固有知識寄り
- **入れないことでまた同じミスをしそうか？**
  - Yes → global `AGENTS.md` か checklist に向く
  - No → doc だけで十分なこともある
- **既存skillやdocsを複数またぐ「入口」や「順番」が本体か？**
  - Yes → orchestration skill / checklist候補
  - No → 既存skillのreferenceやassetへの吸収を優先
- **すでに昇格済みの内容がリポジトリの `AGENTS.md` や docs に残っているか？**
  - Yes → リポジトリ固有差分だけを残す cleanup 候補
  - No → そのままでよい

## 昇格の粒度

昇格は新しい skill を増やすことだけではない。
小さいが汎用的な知見は、まず既存 skill の `references/`、`assets/`、または既存 template へ吸収する。
`references/revisit-candidates.md` は保留箱であり、汎用知見の保存先そのものではない。

ただし、既存skillへ分解できることと、新しいskillが不要なことは同じではない。
複数skillやdocsを正しい順番で呼ぶことが価値なら、部品を重複させずに入口だけを持つ orchestration skill として昇格する。

## 大事なこと

`codex-toolkit` は物置ではない。
「また使う」より一段深く、**次の作業の質を確実に上げるもの**だけを置く。

共通化した後に元リポジトリや関連リポジトリへ古いコピーが残ると、次第に drift する。昇格と同時に「どこを消すか」まで考える。standalone な補助棚を増やすより、関連 skill から辿れる `references/` に寄せる。
