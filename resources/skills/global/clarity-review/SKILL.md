# Clarity Review

コードの可読性、責務分担、変更容易性を点検し、いきなり patch せずに改善方向を整理する workflow。

## 関連 skill との境界

- `clarity-review`: 読みにくさ、責務集中、重複、命名、変更容易性を広く見る。
- DDD、project分離、Core / UI / adapter / provider / persistence の境界を今切るか延期するかが主題の時は、配備済みの境界設計用手順があるか確認する。
- 迷う場合はまずこの skill で責務マップと改善 option を出し、境界導入が主要論点になった時だけ専用手順へ進む。

## 使う場面

- ユーザーが「コードがわかりづらくないか」「設計を見たい」「整理したい」「リファクタしたい」と言った時。
- 機能追加前に、今の構造が次の変更に耐えられるか確認したい時。
- 既存実装の責務が一つの file / class / module に集まり始めている時。

## 手順

1. 目的と読み取り範囲を確認する。
   - 何を作っている リポジトリか。
   - 今後どんな変更が入りそうか。
   - 今回は review だけか、合意後に refactor まで進めるか。
2. すぐ編集せず、必要な code を読む。
   - 主要 entry point、状態管理、外部 I/O、UI / presentation、test / smoke test を見る。
   - 既に review 済みの範囲を重複して深掘りしすぎない。
3. 問題を分ける。
   - 今すでに読みにくい問題。
   - 今は読めるが、次の成長で詰まりそうな問題。
   - 好みの問題に近く、急いで直さなくてよい問題。
4. 2〜3個の改善方向を出す。
   - 例: A = 小掃除、B = 責務分割、C = 現状維持。
   - それぞれの tradeoff、リスク、推奨条件を書く。
   - 意味のある選択がある時は、勝手に決めずユーザーの選択を待つ。
5. 合意後に refactor する。
   - 既存挙動を変えない。
   - file の責務を明確にし、名前で意図が読めるようにする。
   - 大きな抽象化を増やしすぎない。
6. 検証する。
   - build / test / smoke test のうち、そのリポジトリで現実的な最小確認を行う。
   - 通った確認、意図的に省いた確認、sandbox / tooling 由来の失敗を分けて報告する。

## references の読み分け

- しきい値、score、bonus、ranking、通知理由の意味がズレそうな時は `references/scoring-semantics.md` を読む。

## 出力

review だけの場合:

- 全体評価
- 良い点
- 読みにくさまたは将来の詰まりポイント
- 改善 option と tradeoff
- 推奨する次の1手

refactor まで行った場合:

- 変更した file
- 何をどこへ分けたか
- 挙動を変えていないこと
- 検証結果
- 次に分けるならどこか

## optional サブエージェント lane

ユーザーが明示的に サブエージェント / 並列 review を求めた時だけ、`clarity-scout` 的な explorer lane を立ててもよい。役割は「編集せず、責務マップと改善 option だけ返す」ことに限定する。
