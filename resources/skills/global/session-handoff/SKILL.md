# セッション引き継ぎ

## 手順

1. 書き始める前に、現在のリポジトリ状態を確認する。
   - 現在の branch、status、直近 commit、関係の深い project docs を読む。
   - 何が変わり、何を検証し、何が未解決かを切り分ける。
2. 長期記録と短期引き継ぎを分ける。
   - リポジトリに長期の開発記録があるなら更新する。
   - 直近の再開用に、短い次セッション向けメモを作成または更新する。
3. 新しい agent がすぐ再開できるように引き継ぎを書く。
   - 現在地、完了した作業、正確な再現 / 検証コマンド、次にやるべき作業、未解決の判断、重要ファイルを含める。
   - 曖昧な要約より、観測した事実やコマンド出力を優先する。
   - 成果物や確認結果を書く時は、対象ファイル、実行コマンド、exit code または判定、未実施理由を省略しない。
   - 成果物を作ったエージェント、統合したエージェント、保存先を分けて書き、サブエージェントやツールの観測を親エージェント自身の観測として扱わない。
   - delegated lane が途中停止している場合は、lane id、現在工程、完了済み工程、canonical artifact、親が代行した unblock、次に渡す再開入力を分けて書く。
   - 採用済みの内容は正本へ移し、handoff には未解決論点と次の入口だけを残す。
4. 引き継ぐ前に検証する。
   - 実用的な範囲で、そのリポジトリに合った確認を実行する。
   - 通った確認と、意図的に省いた確認を記録する。
5. 今回の作業で再利用できる知見が生まれていないか確認する。
   - skill / template / 運用ガイダンスへ昇格できそうなら、`toolkit-promotion` skill で候補か判定する。
6. 本当に受け渡し点にするなら、状態を永続化する。
   - 適切なら commit する。
   - push は、ユーザーが求めた時か リポジトリの運用で前提になっている時だけ行う。
7. 短い次セッション開始プロンプトを用意する。
   - 最初に読むべきファイルを明記する。
   - 現在のボトルネックと、最初に進めるべき作業を書く。
   - 形式に迷ったら、引き継ぎ本文は `assets/next-session-note.md`、開始プロンプトは `assets/next-session-start.md` を雛形として使う。
   - 採用済みの変更を正本へ反映する handoff なら、`assets/source-integration-handoff.md` を雛形として使う。

## references の読み分け

- milestone 完了前や長期記録の更新後に、判断理由が後から読めるか確認したい時は `references/decision-gap-audit.md` を読む。

## 書き方

- 直近の引き継ぎは、数分で読める長さに抑える。
- 長期の判断理由は、引き継ぎメモだけでなく開発記録にも残す。
- 不確実さを潰さず、観測済みの事実と仮説を分ける。
- リポジトリに明示的な言語やドキュメント規則があるなら、それに従う。
- 「確認済み」「未確認」「失敗したが原因が切り分け済み」を混ぜずに書く。
