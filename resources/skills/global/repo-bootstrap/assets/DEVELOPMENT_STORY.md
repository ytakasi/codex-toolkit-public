# DEVELOPMENT STORY

このドキュメントは、実装を含む作業の経緯、判断理由、検証結果を残すための長期記録です。
逐次ログをそのまま積むのではなく、後から「なぜそうしたか」を追える開発ストーリーとして保ちます。

## この開発記録の使い方

- 実装を含む変更をした時は、同じ作業単位で内容、判断、理由、検証結果を追記する。
- 小さな修正でも、設計判断や運用判断がある場合は短く残す。
- 純粋な誤字修正や文章整理だけの変更は、必要がなければ追記しなくてよい。
- 一時的な迷走より、採用した方針、重要な代替案、今後の注意を優先して残す。

## 判断を書く時の問い

重要な判断が抜けそうな時は、以下を短く埋める。
全部を毎回書く必要はないが、後から「なぜそうしたか」が分からなくなりそうなものは残す。

- 数値しきい値: なぜその値か、どのユースケースや運用感覚を表しているか。
- 対象 / 除外: なぜ入れるか、なぜ落とすか。後で広げる条件は何か。
- 現実データ確認: dry-run、fixture、UI readback、人手確認のどれで確かめたか。
- 運用事故の芽: 設定反映、state path、secret、DB、通知履歴、scheduler、deploy手順に影響がないか。
- v1完成境界: 何が揃ったら完成扱いにしたか、何を follow-up へ送ったか。
